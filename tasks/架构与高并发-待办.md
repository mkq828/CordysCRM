# 架构与高并发 — 待办

> 状态：**暂缓（等上线 + 压测数据）**。来源：2026-10 由「这套系统支持高并发吗」讨论引出。

## 现状结论（已确认）
- 单体 Spring Boot 3 + Java 21（虚拟线程已开 `spring.threads.virtual.enabled=true`）+ 单 MySQL + Redis。
- HikariCP：主库 100、定时任务独立 50；Redis 扛 Session/缓存/验证码/权限缓存。
- 定位是中小企业多租户 CRM，**不是互联网级高并发架构**。
- 结论：现状够用，别为「高并发」提前过度改造。

## 提量路径（按顺序，不要跳）
1. **数据库读写分离（主从）** —— 性价比最高，第一刀。
2. **分库分表** —— 最大工程：引入中间件、改所有 SQL、迁移现有数据，风险高。
3. **消息队列** —— 耗时任务（AI 生成/导出/短信）削峰填谷。

## 前置条件（没满足前不启动任何一项）
- 上线并稳定跑一段时间。
- 压测拿到真实 QPS + 慢 SQL 清单 + 租户数/数据量增长趋势。
- 数据证明「数据库是瓶颈」后再动手，且**一样一样来、各自单独验收**。

## 为什么现在不做这三样
- 没上线、没压测、没数据，现在做是「猜瓶颈」。
- 分库分表是重型改造，会拖慢上线、引入大量回归 bug 风险，且当前无数据证明需要它。
